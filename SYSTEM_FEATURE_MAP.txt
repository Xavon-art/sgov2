================================================================================
SECTION 1. UNIFIED STATUS MODEL (TARGET)
================================================================================

Canonical statuses: PENDING, DRAFT, UNDER REVIEW, RETURNED, APPROVED,
REJECTED, OVERDUE.
Modifier flag: LATE SUBMISSION (derived; not a status value).

Rules implied by the brief and by the existing system:
- UNDER REVIEW and RETURNED are separate. A returned item is back with the
  submitting unit and must be resubmitted; it is not rejected.
- OVERDUE is derived from a due date and an open status. It is not a stored
  lifecycle state in task_assignments (see 20260101002400_task_assignments.sql).
- LATE SUBMISSION is a flag on a submitted item whose submitted_at is after its
  due date. It is independent of OVERDUE.
- The current TS model in src/lib/status.ts has no `returned`; that is a direct
  gap against this header.
- The latest migration, 20260101004600_unified_status_model.sql, also has no
  `returned`. It maps every returned/needs-revision/superseded value to
  `rejected`, which loses the "send back for changes" state. This is the single
  largest design conflict found (Section 8).

================================================================================
SECTION 2. ROLES, SHELLS, AND ACCESS
================================================================================

Account scopes: owner, reviewer, self (WorkspaceRole.accountScope).
Workspace side: usg or lsg, resolved from the session by the database.
Governance model: federated or unitary (isCentral / governanceModel).
Centralized mode hides unit-specific items (People & Units, Published chart
action, LSG Resolutions); LSG unit identity stays in Profile.

Shell: src/components/dashboard/AppShell.tsx wraps every dashboard page.
Nav: src/components/dashboard/usg-nav.ts and lsg-nav.ts.
Context: src/components/dashboard/dashboard-context.tsx (role, unit, refresh).
Guards: server layouts/pages call currentAccount() and redirect; owner-only
pages also render <NotAvailable /> (src/components/dashboard/NotAvailable.tsx)
instead of silently failing. `/usg/officers` is owner-only this way.

USG access summary:
- owner: full Manage, People & Units, Government structure with the published
  chart action, Profile and Customization.
- reviewer: Government structure queue, Documents, Budget, Feedback.
- self: Profile and Customization only.
LSG access summary:
- all LSG users get the unit's Manage tabs and Request/Events/Surveys.
- Resolutions is hidden when centralized.

SECTION 6. DEEP TRACES OF THE FOUR PARTIALLY-WIRED FEATURES
================================================================================

6.1 RESOLUTIONS
1. User opens /usg/request?tab=resolutions (or /lsg/...). RequestSection reads
   the tab param and renders ResolutionPanel.
2. Panel GETs /api/resolutions. Route calls list_resolutions with the session
   token; SQL scopes by side/unit and returns rows. Rows are typed as
   ResolutionRow; status is a plain string.
3. Create: panel POSTs /api/resolutions. Route calls create_resolution with
   title/body/files. SQL inserts without a status, so the column default
   'submitted' applies.
4. Review: USG panel POSTs /api/resolutions/[id]/review with
   decision in {under_review, approved, returned, published} and a remark.
   Route validates the id and decision, requires a remark for returned, then
   calls review_resolution. SQL enforces USG reviewer role from the session and
   writes the decision.
5. Publish: decision=published flips the public record; the public page reads
   approved/published rows.
6. What works: list, create, review, publish, file upload, public read.
7. What does not: the TS ResolutionDecision type omits under_review and
   published and includes rejected; rows are not passed through normalizeStatus,
   so a legacy 'submitted' row does not match the unified badge map; 04600
   removes submitted/returned/published from the constraint, so create and
   return/publish break if it is applied.

6.2 PROPOSALS / REQUIREMENTS
1. User opens Request > Requirements. RequirementsPanel GETs /api/proposals.
   Route calls list_proposals and returns rows.
2. Create: panel POSTs /api/proposals with program/title/description/type/date/
   budget. Route calls create_proposal. SQL inserts status 'submitted' (or
   'requirements_requested' when requirements are attached).
3. Start review: POST /api/proposals/[id]/start-review -> start_proposal_review
   -> status 'under_review'.
4. Review: POST /api/proposals/[id]/review with decision and optional
   requirements. Route passes decision/remark/requirements to review_proposal
   with no whitelist. SQL moves to requirements_requested / approved / rejected /
   returned.
5. Unit requirement submission: POST .../requirements/submit -> submit_
   proposal_requirements -> requirement rows 'submitted'; proposal may move to
   under_review.
6. Verify: POST .../requirements/verify -> verify_proposal_requirements ->
   requirements 'accepted' or 'waived'.
7. What works: the full happy path exists and is wired.
8. What does not: RequirementsPanel keeps its own PROPOSAL_STATUS map with
   legacy strings, so unified rows render without a label/colour; 04600 keeps
   requirements_requested but remaps the rest; review route has no decision
   whitelist; there is no explicit "Submit for review" action separate from
   create.

6.3 ACCOMPLISHMENT REPORTS
1. User opens Events > Accomplishment. AccomplishmentPanel GETs
   /api/accomplishment-reports -> list_accomplishment_reports -> rows.
2. Create: panel POSTs /api/accomplishment-reports with event id, narrative,
   files. SQL inserts status 'submitted'.
3. USG review: panel POSTs /api/accomplishment-reports/[id]/review with
   decision. The panel currently sends approved/rejected, but review_
   accomplishment_report expects acknowledged/returned. The route forwards the
   value, so SQL rejects the decision or returns an error reason.
4. What works: list, create, file upload, attachment download.
5. What does not: review decision vocabulary (approved/rejected vs acknowledged/
   returned) breaks the USG action; TS type and SQL disagree; 04600 removes
   acknowledged entirely and maps to approved/rejected, so the mismatch persists
   in a different form.

6.4 PUBLIC FEEDBACK FORM (/feedback/f/[token])
1. Visitor opens /feedback/f/[token]. The server page calls
   getPublicFeedbackForm(token) from src/lib/feedback-forms.ts, which resolves
   the token to a form and its questions, and requires form status 'open'.
2. If unavailable, the page renders an unavailable state. If available, it
   renders PublicFeedbackForm.
3. Submit: client POSTs /api/feedback/public/[slug] with answers. Route calls
   submit_feedback_form_response. SQL inserts a response with status 'new'.
4. Status poll: client GETs /api/feedback/public/status?token=... to confirm
   acceptance.
5. What works: token resolution, render, submit, duplicate guard, public status
   polling, no session required.
6. What does not: 04600 rewrites feedback_forms.status from open to pending and
   closed to rejected, while getPublicFeedbackForm and the public route still
   require 'open'. If 04600 is applied, every public form becomes unavailable.
   The route name is correct (/api/feedback/public/[slug]); there is no
   /api/feedback/f/[token] endpoint and none is needed.

SECTION 8. STATUS DRIFT (MIGRATION 04600 VS RUNTIME)
================================================================================

Migration 20260101004600_unified_status_model.sql is the newest migration. It
rewrites CHECK constraints on: task_assignments, budget_requests, proposals,
events, structures, personal_requests, feedback_forms, feedback_entries,
document_catalog, resolutions, accomplishment_reports (and related tables).
It maps many legacy values to pending/approved/rejected.

The runtime code was not updated to match:
- No `returned` anywhere in the 04600 constraint set. RETURNED is required by
  the brief and is the core of the review loop.
- No `published` for resolutions/proposals; publication becomes approved.
- No `open`/`closed` for feedback forms; public forms require open.
- No `cancelled` for events; cancel path has no valid value.
- No `acknowledged` for accomplishment; review RPC expects it.
- No `requirements_requested` in the target set (03050 keeps it).
- No `granted`/`declined`/`needs_revision`/`submission_required`/`withdrawn`/
  `expired` for personal requests.
- No `superseded` for structures; republish loses history semantics.

Writers that still emit legacy values (would fail post-04600):
- create_resolution / review_resolution (submitted, returned, published).
- create_proposal / review_proposal / submit_proposal_requirements
  (submitted, requirements_requested, returned, published).
- create_event / claim_event / decide_event (upcoming, claimed, honored,
  not_honored, cancelled).
- decide_personal_request / resubmit (granted, declined, needs_revision,
  submission_required, withdrawn, expired).
- submit_structure / review_structure / publish_structure (submitted, returned,
  superseded).
- review_budget / budget open counts (submitted, returned).
- review_accomplishment_report (acknowledged, returned).
- set_feedback_form_status / submit_feedback_form_response (open, closed, new,
  acknowledged).
- create_task (inserts without status, relying on default assigned).
- acknowledge_feedback (acknowledged).

Readers that filter legacy values (would show nothing post-04600):
- /api/overview: submitted, claimed, upcoming, open.
- /api/tasks: assigned, in_progress, done (submitted already missing).
- Monitoring SQL CASE (03240).
- Budget open counts (02300).
- Public feedback loader: open.
- Structures queue: submitted/returned.

Conclusion: either 04600 is not applied (then TS/libs already expect unified
values that the DB never produces) or it is applied (then most write paths
fail). Both states are inconsistent. P1 must reconcile SQL, TS, and UI in one
migration plus code change before any new feature work.
